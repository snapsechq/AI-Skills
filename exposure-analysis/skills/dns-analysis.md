# DNS Analysis & Subdomain Takeover Skill

## Objective

Act as a **DNS & Subdomain Takeover Specialist**. Systematically analyze DNS records across in-scope assets to detect **dangling CNAME records, orphaned cloud infrastructure, vulnerable nameserver delegations, and second-order takeovers via external JavaScript dependencies**.

---

## Methodology

### Step 1: Subdomain Extraction & DNS Record Enumeration
Extract all in-scope subdomains from `checklist.md` / `assets.json`:
```bash
python3 scripts/query_assets.py session-<session_id>/assets.json --list-subdomains
```
For each target subdomain, query and record full DNS record types:
```bash
# Query CNAME records
dig +nocmd +noall +answer <subdomain> CNAME

# Query A / AAAA records
dig +nocmd +noall +answer <subdomain> A

# Query NS records (for delegated subdomains)
dig +nocmd +noall +answer <subdomain> NS
```

---

### Step 2: First-Order Subdomain Takeover (Dangling CNAMEs)
Identify subdomains configured with a `CNAME` pointing to a third-party cloud service or SaaS provider where the tenant resource has been deleted, but the DNS pointer remains active.

#### High-Risk Cloud Providers & Error Fingerprints:
| Provider | CNAME Target Pattern | Unclaimed Signature / Fingerprint |
|---|---|---|
| **AWS S3** | `*.s3.amazonaws.com`, `*.s3-website-*.amazonaws.com` | `NoSuchBucket` / `The specified bucket does not exist` |
| **GitHub Pages** | `*.github.io` | `There isn't a GitHub Pages site here.` (HTTP 404) |
| **Heroku** | `*.herokuapp.com` | `No such app` / `herokucdn.com/error-pages/no-such-app.html` |
| **Azure App Service** | `*.azurewebsites.net`, `*.trafficmanager.net` | `404 Web Site not found` |
| **Shopify** | `*.myshopify.com` | `Sorry, this shop is currently unavailable` |
| **Zendesk** | `*.zendesk.com` | `Help Center Closed` |
| **Fastly CDN** | `*.global.prod.fastly.net` | `Fastly error: unknown domain` |
| **Surge.sh** | `*.surge.sh` | `project not found` |
| **Readme.io** | `*.readme.io` | `Project doesnt exist` / `Subdomain not found` |

#### Safe Verification Process:
1. Confirm the CNAME chain terminates at the third-party provider domain.
2. Probe HTTP/HTTPS responses with `curl -s -I -L https://<subdomain>` or `scripts/probe_asset.py`.
3. Check if the body contains the exact provider-specific "unclaimed tenant" error signature.
4. **Safety Rule**: Never claim the bucket or register the third-party resource. Verifying the error fingerprint and CNAME pointer is sufficient proof.

---

### Step 3: Dangling Nameserver (NS) Takeovers
For delegated subdomains or zones (e.g. `dev.corp.example.com`):
* Check if delegated `NS` records point to third-party cloud DNS (e.g. AWS Route 53, Azure DNS, DigitalOcean).
* If the delegating nameserver returns `SERVFAIL` or `REFUSED`, test whether the hosted zone was deleted on the provider while the parent domain retains the delegation.
* An orphaned NS delegation allows an external party to re-register the hosted zone and gain full DNS control over the subdomain.

---

### Step 4: Second-Order Takeovers (via JS & External Assets)
Analyze external resources loaded by in-scope web applications for expired domains or unclaimed cloud buckets:

1. **Extract External Dependencies**:
   * Inspect HTML and scripts extracted in `skills/js-analysis.md`:
     - `<script src="...">` tags
     - `<link rel="stylesheet" href="...">`
     - CSS `@import` rules
     - Cloud storage URLs (e.g. `https://<company>-assets.s3.amazonaws.com/...`)
2. **Check for Expired Third-Party Domains**:
   * For every external domain referenced in frontend scripts:
     ```bash
     # Check if the external domain resolves
     dig +nocmd +noall +answer <external_domain> A
     ```
   * If the external domain returns `NXDOMAIN`, check WHOIS availability. If an active script source domain is available for registration, an attacker can claim it and achieve full Stored XSS / code execution on the parent web application.
3. **Check for Unclaimed Dependency Buckets**:
   * If frontend scripts or assets load from an S3 bucket or cloud storage URL, query the bucket endpoint directly:
     ```bash
     curl -s https://<referenced-bucket>.s3.amazonaws.com/
     ```
   * If it returns `NoSuchBucket`, the application is vulnerable to second-order script takeover.

---

### Step 5: Non-Findings vs. Real Exposures
Follow the strict validation constraints in `resources/finding_Validation_example.md`:

* **Reject (Non-Findings)**:
  * Active CNAMEs pointing to live, properly claimed third-party tenants (e.g., active Zendesk help desk showing corporate branding).
  * Standard application `404 Not Found` generated by an in-house web server (e.g., Nginx, Apache, Node.js) rather than a cloud provider's unclaimed tenant page.
  * Providers requiring strict pre-validation of domain ownership (e.g., modern CloudFront / Azure custom domain validation) unless demonstrable bypass exists.
  * Speculative takeover claims without verified CNAME records and matching provider error fingerprints.
* **Report (Confirmed Exposures)**:
  * Subdomains with active CNAME pointing to an unclaimed cloud resource returning confirmed provider error signatures (`NoSuchBucket`, `No such app`, `There isn't a GitHub Pages site here`).
  * In-scope web applications loading JavaScript from an expired domain (`NXDOMAIN`) or an unclaimed S3 bucket (`NoSuchBucket`).
  * Dangling nameserver delegations pointing to unassigned cloud DNS provider zones.

---

## End Goal

Deliver validated findings for DNS and asset-level takeover risks that:
1. Provide the complete CNAME / NS resolution chain.
2. Include the observed provider error signature proving the resource is unclaimed.
3. Demonstrate clear security impact (arbitrary web defacement, cookie theft, session hijacking, or Stored XSS) without executing unauthorized claims.
