# Output Rules & Reporting Constraints

All exposure findings generated by the agent must strictly comply with the rules and constraints below.

---

## 1. Output Format

* **JSON Only**: The entire output must be a single raw JSON array matching `resources/exposure_schema.json`.
* **No Markdown Wrapper**: Do NOT enclose the output in markdown code blocks (e.g. ````json ... ````).
* **No Conversational Text**: Do not include explanations, headers, footers, analysis, or conversational commentary outside the JSON array.
* **Empty Result**: If no verified real-world exposures are confirmed, return exactly:
  ```json
  []
  ```
* **Deduplication**: Do not report findings that were already provided in the input dataset. These are known issues and creating duplicate findings is prohibited.

---

## 2. Field Constraints

| Field | Constraint | Description |
|---|---|---|
| `associatedAsset` | Object (`type`, `value`, `subdomain`) | Target asset where exposure was identified. |
| `exposure_tag` | **Required**, `<issue_slug>:<normalized_target>` | Deterministic tag for deduplication (see `resources/exposure-tags.md`). Must be identical for identical findings. |
| `title` | **10–15 words** | Concise technical title describing confirmed security issue. |
| `description` | **Max 50 words** | Concise technical description of observed and validated issue. |
| `severity` | `critical` \| `high` \| `medium` \| `low` | Real-world impact severity (see Severity Scale below). |
| `confidence` | `high` \| `medium` \| `low` | Evidence-backed confidence level (see Confidence Scale below). |
| `impact` | **Max 50 words** | Concrete security consequence an attacker can achieve. |
| `remediation` | **Max 50 words** | Practical remediation required to eliminate demonstrated exposure. |
| `steps_to_reproduce` | **Max 70 words** | Clear markdown steps (numeric or bulleted) allowing exact reproduction. |
| `references` | **Max 3 URLs** | Relevant vulnerability references / CWE / vendor security docs. |
| `attack_path` | Array of steps | Realistic sequential attack path (see Attack Path Rules). |

> **Sensitivity Warning**: Do NOT include sensitive information like live credentials, passwords, API keys, tokens, or PII in the output unless absolutely necessary to describe the finding.

---

## 3. Attack Path Requirements

For every reported finding, provide a realistic attack path:

* Each step must include `step` (description) and `status` (`confirmed` or `inferred`).
* **Confirmed**: Directly demonstrated through active or passive evidence.
* **Inferred**: Logical consequence supported by evidence. Never label an inferred step as confirmed.
* The path must start at the attacker entry point (e.g. internet-facing endpoint) and terminate at the verified impact.
* Do NOT extend the path into unsupported claims (e.g. "Full database wipeout", "Domain takeover") without evidence.

---

## 4. Severity & Confidence Definitions

### Severity Scale
* `critical`: Direct compromise of critical systems, identity infrastructure, sensitive financial operations, major data access, remote code execution.
* `high`: Significant unauthorized access, account takeover, administrative compromise, privilege escalation.
* `medium`: Limited unauthorized access, data exposure, security boundary bypass with moderate impact.
* `low`: Real security impact, but genuinely limited. Discard any technical issue that has zero practical impact.

### Confidence Scale
* `high`: Directly validated with strong evidence (e.g., successful authenticated response, exposed git metadata).
* `medium`: Vulnerability is validated but some environmental impact details are inferred.
* `low`: Meaningful evidence exists, but full scope cannot be safely probed. Never report purely hypothetical findings.

---

## 5. Reporting Threshold Checklist

Before adding any exposure to the final JSON, ensure the answer to all of the following is **YES**:

1. Can an external attacker reach the affected functionality?
2. Is there a concrete, demonstrated security weakness?
3. Did testing validate that the security boundary was violated?
4. Is there a meaningful real-world security consequence?
5. Can the finding be explained without relying on multi-step hypothetical assumptions?

If any answer is **NO**, **omit the finding**. Always prefer omission over speculation.
